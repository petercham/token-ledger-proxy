# Token 账本反代工具（Strata / Basalt 兼容）

你有一台自己托管的推理引擎，团队都在用它——然后你会想知道：**谁在用、用了多少、这台机器还扛不扛得住**。这套小工具就是回答这三个问题的，一个进程装到任何机器上就能跑。

- **账按人算，数字是官方的。** 每一次调用按 API key 的指纹归到具体的人，token 数直接取引擎返回的官方用量字段——不解析日志、不猜、并行批处理也不失真。
- **想知道省了多少钱，一键算。** 网页报表内置「省钱计算器」：把本地跑掉的 token 量按 22 款主流模型的公开 API 牌价（随包的 `api-price-table.csv`，逐家官方页核验）折算——同样的用量走云端要花多少，一眼看到（截图见第四节）。
- **长生成不掐线。** 响应头立即发出、上游每到一个数据块就转发刷新，首字节约 0.01 秒。很多「号称流式」的中间层实际是整包缓冲——引擎生成几分钟，中间设备一个字节收不到，读超时一到就掐线报 502。这个坑我们用实机 A/B 验证过并修掉了，本包是修好的版本。
- **开箱就有监控页。** 一个网页看全这台机器的每张显卡（异构混插、按 UUID 绑卡不串卡）、内存、磁盘、网卡、PCIe 实际链路、CPU 实时频率——读数与任务管理器同源。
- **它自己养活自己。** 进程掉了 5 秒内自动拉起；换版本时检测到有人在用会直接拒绝切换，不会把全队弄断。
- **零依赖。** 主链只用 Python 标准库——不需要数据库、不需要第三方库、不需要任何特定宿主环境。Windows / Linux 有在岗实机；macOS 走同一套启动件（launchd 示例在包内），路径与端口分支经平台模拟验证。

装上之后你在 `/monitor` 一页看到的就是这些（下面是真实在岗机器截屏，非示意图）——上半页是这台机器的每个硬件，逐卡逐盘逐网卡：

![监视页·硬件区](docs/monitor-hardware.png)

下半页是账：每一次请求的输入/复用/输出 token、预填充与解码速率、显存命中率、耗时，底部一行开账以来的合计；「对话缓存」卡直接告诉你 KV 复用了多少——上面这台机器 82% 的输入 token 是复用的，这就是为什么它的解码能稳住 110+ tok/s：

![监视页·账本区](docs/monitor-ledger.png)

（页面自带深浅两套主题，截图为浅色态；硬件读数每秒刷新，卡按显卡 UUID 绑定，异构混插不会串卡。）

**代价也先说清楚**（详见第九节）：因为它站在请求链路上，它挂了团队就断——所以守护进程和切换纪律是包的一等公民，不是可选项。我们宁可把边界写重，也不卖一个「装上就忘」的幻觉。

**三分钟上手**：

```
git clone https://github.com/petercham/token-ledger-proxy.git
cd token-ledger-proxy
python bootstrap.py --init      # 从模板生成本机配置
python bootstrap.py --check     # 只读自检，不动任何服务
bash start.sh                   # 试跑（Linux/macOS；Windows 用 start.bat）
```

账本数据、日志、每台机器自己的 `config.json` 一律不入库（`.gitignore` 锁死），`git pull` 升级永不动你的数据。稳定版本看 tag（如 `rev8`），`main` 是最新已验证形态。

## 一、和「自己写个脚本读引擎日志」有什么不一样

给自托管引擎记账，最直觉的做法是旁路读日志。这条路我们完整踩过，它的天花板是结构性的，不是写得好坏的问题：

| | 旁路读日志的做法 | 本工具（站在请求链路上） |
|---|---|---|
| 算到具体的人 | 做不到——日志里没有身份 | 靠 API key 指纹对应到姓名 |
| 数字准不准 | 引擎并行批处理时日志归属会失真（我们在 5090 实测自报口径约 3.9%） | 直接读引擎返回的官方用量字段，不猜 |
| 会不会影响业务 | 不会，它在旁边看 | **会**——它站在业务中间，挂了团队就断 |
| 常驻进程 | 采集器 + 定时器 + 监控页，3 个 | 1 个服务 + 1 个守护进程 |
| 掉线了 | 没人管 | 5 秒内自动补岗 |

一句话：**换到请求链路上，是拿「故障面变大」换「归人、数字准、结构简单」**。这笔交换值不值，第九节把代价逐条写开了，看完再装。也正因为故障面变大，包里带了守护进程和「有会话时禁止切换」的规矩——这两样不是可选项，别拆开只拿代理脚本。

## 二、安装（三个平台通用前四步）

**第 1 步**：取包。新机器 `git clone`（地址见上），已有本包的机器 `git pull`；也可以直接把整个目录拷到目标机任意位置。目录里没有写死任何盘符或用户名，放哪都行。

**第 2 步**：生成配置。

```
python bootstrap.py --init
```

会在目录里生成 `config.json` 和 `data/`。**已经存在 config.json 时不会覆盖**，可以反复跑。

**第 3 步**：按目标机实际情况改 `config.json`，至少看这几项：

| 字段 | 填什么 | 例子 |
|---|---|---|
| `listen` | 团队接入的端口，按实际机器填；看门狗和切换工具会自动跟随 | `0.0.0.0:8080` |
| `upstream` | 引擎真实监听地址 | `http://127.0.0.1:8787` |
| `out_dir` | 账本和报表放哪 | `@here/data` |
| `watchdog_lock_port` | 看门狗自己的防重复端口，**可选**；必须与 `lock_port` 不同 | `43176` |

`web_root` 字段**已弃用**：监控页改为工具自带的 `/monitor`（见第六节），不再往任何外部页面注入脚本。旧配置里留着这个字段不会报错，可以直接删。

**只改 `listen` 一处即可换端口**：`ledger_watchdog.py` 与 `switch_proxy.py` 会从同一个 `config.json` 读取该端口，无需另改脚本、也无需给它们传 `--port`。`lock_port`（反代进程用，默认 `43177`）与 `watchdog_lock_port`（看门狗用，默认 `43176`）是两个独立的防重复端口，通常都不用动；若要改，`watchdog_lock_port` 可直接在配置里配，且务必与 `lock_port` 保持不同，否则两个进程会抢同一个端口。

路径可以写 `@here/data`（配置文件所在目录）、`@pkg/data`（工具包目录）、`~/data`（用户主目录）、相对路径或绝对路径，三种系统都认；**纯相对路径按配置文件所在目录解析**，不随当前工作目录漂移。`listen` 想同时接 IPv6 / IPv4 就写 `[::]:8080`。

拿不准怎么填时，看 `config-examples/` 里两份真机形态样例：

| 样例 | 是什么 | 关键示范 |
|---|---|---|
| `config-examples/windows-5090-single-gpu.json` | Windows 单卡终端的**在岗实机抄录**（去掉了人名指纹），2026-11-17 起一直在跑 | `listen ":::8080"` IPv6 双栈门面 + 引擎退环回 `127.0.0.1:8787`；lock 端口为避让旧链改值的示范 |
| `config-examples/ubuntu-pro5000-4090-dual-gpu.json` | Linux 双卡工作站的**装配参考**（按模板缺省组装，非实机抄录） | 双卡无需任何配置项（监控按 UUID 自动逐卡发现）；缺 `psutil` / `nvidia-smi` 自动降级不影响记账 |

样例只示范结构与端口口径，不含真实地址、指纹、姓名；`key_labels` 一律留空，按第三节自己填。

**第 4 步**：只读自检，确认没配错。

```
python bootstrap.py --check
```

它会检查文件齐不齐、数据目录能不能写、端口有没有被占、引擎连不连得上、显卡工具在不在、`key_labels` 填得对不对。**不会启动或停止任何服务**，也不会发业务请求。

### 各平台怎么启动

`start.sh` / `start.bat` 是**交互式试跑**用的：守护进程在前台运行，关掉终端、SSH 断开或会话被清理，守护进程和它拉起的服务会一起消失（见第九节第 7 条）。**生产必须安装 `service-examples/` 里的自启件**，让守护进程脱离会话常驻。

| 平台 | 交互式试跑（仅验证包能用） | 生产必须装 |
|---|---|---|
| Windows | 双击 `start.bat`，或命令行 `python ledger_watchdog.py` | **启动夹里放一个指向** `service-examples/Token ledger watchdog.vbs` **的快捷方式**（VBS 本身留在包目录，不要复制过去） |
| Linux | `bash start.sh`（或先 `chmod +x start.sh` 再 `./start.sh`） | `service-examples/token-ledger.service`（systemd，`Restart=always`） |
| macOS | `bash start.sh`（或先 `chmod +x start.sh` 再 `./start.sh`） | `service-examples/com.token.ledger.plist`（launchd，`KeepAlive`） |
| 开机自启 | 不适用 | Windows 启动夹里放 VBS 的快捷方式；Linux systemd；macOS launchd |

**启动逻辑只有一条**：先起守护进程，由守护进程把服务拉起来。不要在启动脚本里直接 `python collector_proxy.py`——那样服务会跟着某次终端会话一起消失。装好自启件后，用 `python switch_proxy.py --check` 确认服务与守护都在岗；不要靠一个 `Ctrl+C` 就结束的终端窗口长期供服务。Windows 启动夹 VBS（含本包 `service-examples/` 里的示例）给看门狗传了 `--lock-wait 86400`：登录时若旧看门狗还占着防重复锁，新副本会作为热备候补等待，旧看门狗一退出就零缝隙接管，不会「another watchdog already runs」后永久退出。

**为什么 Windows 要用快捷方式**：VBS 按「自己所在目录」去找 `ledger_watchdog.py`；直接把 VBS 复制进启动夹，目录就变成启动夹，主程序找不到且不报错、静默不启动。快捷方式不改变脚本的真实路径，所以能正确定位。目标机若 Python 不在 PATH，设用户环境变量 `TOKEN_LEDGER_PYTHON` 指向 `python.exe` 全路径。

想验证包本身没坏，跑：

```
python bootstrap.py --selftest
```

三套自测（反代转发 / 看门狗 / 监控页）都在临时端口、假数据上跑，**不会碰任何正在运行的正式服务**。

## 三、按人统计怎么配

工具按 API key 的**指纹**（一串 8 位十六进制）归到人，配置里不存原始 key。

1. 算指纹：`python collector_proxy.py --fp <你的key>`
2. 把结果填进 `config.json` 的 `key_labels`，比如：

```json
"key_labels": { "01234567": "张三", "abcdef01": "李四" }
```

**示例指纹是虚构的**，请用 `python collector_proxy.py --fp <你的key>` 实算后再填；本包不附带任何真实 key 指纹或成员姓名。

3. 改完不用重启，下一笔请求就按新名字记。

`key_labels` 里没配的指纹会原样显示成那串 8 位字符，方便你发现「有人用了没登记的 key」。
引擎如果关掉 key 校验、客户端也不带 key，这一笔会记成 `none`——**这种情况没办法归到人**，要按人统计就得给每人发 key。

四个容易踩的坑：

- **`--fp` 算的是裸 key**，别把 `Bearer ` 前缀一起算进去（那会得到完全不同的指纹）。`Authorization` 里的 `Bearer` / `bearer` / `BEARER` 大小写不影响归因，工具按 RFC 7235 统一剥掉；账本每行还会另存 `fp` 原始指纹，便于事后追查。
- **忘记填 `key_labels`** 时，所有请求会显示成 8 位指纹码，报表看着像「多出匿名身份 / 撞车」，其实只是没登记姓名——把 `--fp` 的结果填进配置即可；`bootstrap.py --check` 也会提醒这一条。
- **两个不同指纹填成同一个姓名**会把两个人合并成一条统计；修复前的历史账本行只存了合并后的姓名，**无法从历史数据拆开**。本次起每行都会另存原始 `fp`，新数据可拆，旧数据补不回来。填之前请逐个核对指纹。
- **畸形 `Authorization: Bearer `（前缀后没有 token）**不会记成 `none`，而会记成一个陌生的 8 位指纹：整行经 `strip()` 后变成字面量 `Bearer`，不再匹配 `bearer ` 前缀，于是被当成一把裸 key 去算哈希。这是**有意为之**——客户端把 key 配错时，报表里会立刻多出一个没登记的 8 位码，便于发现配错的客户端；真正完全没带 key 的请求才记 `none`（见第九节第 3 条）。

## 四、账本与报表

- `data/requests-YYYY-MM-DD.jsonl`：每个请求一行，含时间、`key`（姓名或 8 位码）、`fp`（**原始 8 位指纹，永久保留**，用于事后追查 / 拆分合并 / 发现撞码）、模型、输入/缓存/生成 token、耗时、来源 IP、错误码。
- `data/usage-report-YYYY-MM-DD.md`：**日报自动生成**——服务启动时先补查一次，之后每天 `report_hour`:`report_minute` 自动出。日报含「排队闸拦截统计」节：三指标＝拦截入栈次数（当日 `gate-events` 的 `queued` 行数）、最长等待／平均等待（当日 `released` 行 `waited_ms` 的 max/mean），指标按事件文件日归属并如实标注跨日（「N 项等待自前日跨入」）；无逐事件日志的历史日走总账 `queue_wait_ms` 回填口径（带显式标注）；「闸未启用」（config 静态关闸）与「开闸零事件显示 0／—」两态文案分开，开闸判定按日报生成时刻 config 现值，回填历史日时该判定可能失真。
- `data/usage-report.html` + `usage-data.js`：可交互的网页报表（按天 / 快捷周期 / 起止日期，按人筛选）。**需手动生成/刷新**，命令见下；包内没有每天自动刷新它的调用链，日报线程只负责出 `.md` 日报。

想手动重出某一天 / 刷新网页报表：

```
python daily_report.py --config config.json --day 2026-11-05
python daily_report.py --config config.json --all
python html_report.py --config config.json --all
```

第一条出指定那天的 `.md` 日报，第二条补齐全部 `.md` 日报，第三条生成/刷新网页报表（`usage-report.html` + `usage-data.js`）。只有第三条会产出网页报表，想看最新数据就重跑它。新增的 `fp` 字段不影响日报与网页报表的出表逻辑，它们仍按 `key` 分组。

网页报表里点一下「省钱计算器」，当前查询窗口的 token 量就按各家公开牌价折算——下面这张是真机账本近 30 天的实拍：同一批用量走云端 API，最贵一档要 $5,600（≈¥39,300），最便宜的可比模型 $29（≈¥205），而本地跑这两样都是 0——这就是本地算力那一页账的意义。计算器口径写在表下（prompt 新算按 cache-miss 价、KV 命中按 cache-hit 价、生成按输出价；各家分词器差异 ±20%）：

![省钱计算器](docs/savings-calculator.png)

**旧链的历史数据能直接用**：日报要读的核心字段两边一样，把旧的 `requests-*.jsonl` 拷进 `out_dir` 就能混着出报表，不需要转换格式。旧数据没有身份字段，在「按人」筛选里会归到「无 key」一组，这是数据本身没有身份，不是坏了。

## 五、验收清单（部署完照着走一遍）

1. `python bootstrap.py --check` 没有「不合格」项。
2. 服务起来后，`http://<本机IP>:<端口>/health` 返回 `{"ok":true}`。
3. 用团队真实的接入地址发一轮对话，`data/requests-今天.jsonl` 多出一行，里面有正确的 `key`（姓名）、`fp`（8 位码）、`prompt`、`gen`。
4. 发一个流式请求，第一块数据应立刻到达（不是等生成完才一起出来）。
5. `http://<本机IP>:<端口>/ext.json` 能看到全部显卡（每张卡带唯一身份码和显存/编解码利用率）；打开 `http://<本机IP>:<端口>/monitor` 能看到卡片，**每张显卡的波形跟这张卡绑死**——机器重启、槽位号变了也不会把 A 卡的曲线画到 B 卡上。
6. 出日报与网页报表是**两条独立命令**：`python daily_report.py --config config.json --all` 出 `.md` 日报、`python html_report.py --config config.json --all` 出网页报表；网页报表不会自动生成。
7. `python switch_proxy.py --check`：此刻若有人在跑任务，它必须显示拒绝。
8. **部署后自检**：装好 `service-examples/` 自启件后，**关掉启动它的终端 / 结束启动会话**，`/health` 仍返回 200、`/ext.json` 仍返回双卡数据。若任一不可用，说明服务还挂在会话上，别交付使用。

## 六、监控页（自带独立页，不再注入别人的页面）

**打开 `http://<本机IP>:<端口>/monitor` 就是完整监控页**——官方 Strata 监视页的完整复刻加上本包的硬件卡，做成一页融合视图：模型状态卡、Speed（解码 + 预填充双曲线）、每张显卡卡、CPU、系统内存（含交换区）、每块物理硬盘、每个已连接网卡（含合计行）、Context fill 环表、Recent requests 请求表、Conversation cache 卡。页面、样式、图标、脚本、数据接口全部由本工具自己提供（`monitor.html` + `monitor.css` + `monitor-sprite.svg` + `monitor.js`，数据走 `/ext.json` + 转发引擎的 `/metrics`），不加载任何其他网页的资源，也不往任何其他网页里塞东西。硬件数据每秒刷一次；引擎侧数据（请求表、上下文、对话缓存）来自反代原样转发的 `/metrics`——若引擎设了访问密钥，页面会出一个小输入框请你填一次（保存在浏览器本地，与官方控制台页同一个键，之后不用再填）。两个数据源各自独立容错：引擎那边断了不影响硬件卡，采样这边断了不影响请求表。「最近请求」汇总行的起始时刻显示为本地实际日期 `YYYY-MM-DD HH:MM`（如「自 2025-12-17 06:41：…」，2026-11-19 人类口径改版：非星期，跨周无歧义）。

**显卡按卡的唯一身份（UUID）绑定**，包括那张卡的波形历史。nvidia-smi 的槽位号（#0/#1）会在重启、禁用重启网卡后漂移，历史上出过「A 卡的负载曲线画到 B 卡卡片上」的事故，所以本页一律按 UUID 认卡，槽位号只在卡片标题上展示。没有 UUID 的极老驱动退到按卡名认，绝不退回按槽位认。

- 数据接口 `/ext.json`、`/health` **永远可用**，与 `config.json` 里任何字段无关。
- GPU 卡片主数字是 SM 利用率；副行有显存 已用/总量、显存利用率、编码/解码利用率、温度、功率/上限、SM 时钟、驱动模式（WDDM/TCC/MCDM）、**该卡 PCIe 链路**（如 `PCIe Gen5 ×8`，中性信息，不做告警——链路宽度以插槽实际为准，显卡空闲时自动降代省电显示 Gen1 也属正常）。
- **PCIe 线路卡**：单卡简化形态（11-16 五稿）。大数字 = 本轮读速最快那张卡的即时 MB/s；小字固定两行：第一行「当前最高读速」，第二行 = 该卡波形同色的短线图例 + 显卡名；波形只画这条领先线路（历史仍按 UUID 各归各卡，卡切换时曲线换色）。独立图例区已取消。某台机器的 nvidia-smi 不支持每卡吞吐采样时，这张卡会如实显示「不支持」，其余不受影响。
- **硬盘卡**（11-16 六稿形态）：标题 = `#编号 盘符 型号 · 容量`（编号从 1 起显示）；大数字 = 读速数值 + 单位 + 总线规格代码徽章（自动去掉 `Disk N · ` 前缀）；小字固定两行——绿短线引导「读」、橙短线引导「写」。
- **网卡卡**：无线网卡标题就叫「无线网卡」（不出徽章）；有线网卡标题 = 适配器真名 + 「有线」徽章。大数字 = 下行数值 + 单位；小字固定两行——绿短线「下行」、橙短线「上行」。
- **显卡卡标题**序号前置：`#序号 卡名`（与硬盘同款，从 1 起显示）；序号只是对照用——nvidia-smi 槽位号会漂，认卡身份永远按 UUID。
- **CPU 卡也带短线图例**：双插槽时左右小字各一条短线，分别对应左/右两条波形颜色；单插槽也有图例（短线 + 核/线程规格）。波形右线（预填充色）改为跟随所在卡的主色自动加深，图例颜色永远与波形色一致。
- 所有卡片标题恒一行（超长省略号截断）、大数字行定高——各卡「大数字下面的小字」起始高度全部对齐。
- 没有 `psutil` 就少看内存/磁盘/网卡，没有 `nvidia-smi` 就少看显卡——**都不影响记账**。
- **物理硬盘清单**（型号、总线、容量）在 Windows 上通过 PowerShell 的 `Get-PhysicalDisk` 读取；Linux / macOS 没有 PowerShell 时这一项会为空，显卡、内存、网卡和记账都照常工作。

监控页和团队接入是同一个地址、同一个端口，远程打开看到的是这台服务器的数据，不会变成看自己电脑。

**监视页自身故障的退回路径**：`/monitor` 页面本身出问题时，回滚到上一个稳定 tag（`git checkout <tag>`；rev8 之前的老机器如仍持 ZIP 则整包回滚）；注意 `ext.js` shim 只兜「官方页尚未恢复」的过渡显示，**不兜 `/monitor` 故障**。

### 6.1 从旧「注入式」监控升级过来（一次性操作）

本版把监控从「往 Strata 官方控制台页面里注入一行脚本」彻底换成自带独立页。升级时按顺序做：

   恢复后可顺手删掉同目录的 `index.html.orig`，以及页面里若还残留 `<!-- monitor-ext -->` 标记行（用备份恢复后一般已一并消失）。
3. **旧 `ext.js` 退役**：不再需要。包内保留这个文件只为兼容「还没按上面恢复」的页面继续过渡显示；确认所有页面恢复后，可以直接把团队访问入口都改用 `/monitor`。恢复完成前旧注入页仍能正常出卡片（数据接口没变，只是多了四个显卡字段），不会白屏。**注意**：过渡期内旧注入页（ext.js shim）仍按 nvidia-smi 槽位号分桶历史，仍可能把 A 卡曲线画到 B 卡上——它不修复串卡问题，请尽快执行上面的页面恢复，改用按 UUID 绑定的 `/monitor`。
4. `config.json` 里的 `web_root` 字段删不删都行，不会再起作用。

## 七、从旧链迁移 / 回滚

**建议并排跑，不要一刀切**：

1. 旧链保持不动，本工具先用一个**临时端口**起起来。
2. 自己用临时端口跑几天，确认按人统计、日报、监控页都对。
3. 把旧的 `requests-*.jsonl` 拷进新的 `out_dir`（需要历史数据连续的话）。
4. 选一个没人跑长任务的时间，把团队的接入地址切到新端口。旧链先别停，留着随时切回去。
5. 稳定后再停旧链。

**回滚**：把团队接入地址指回引擎端口，停掉守护进程和服务即可。账本文件不会丢。

> 切换前一定跑 `python switch_proxy.py --check`。**有客户端会话时它会硬拒绝**，加 `--force` 也不行——这是用一次真实断连换来的规矩。等没人用了再切。

## 八、日常运维

| 想做什么 | 怎么做 |
|---|---|
| 看服务在不在 | `python switch_proxy.py --check`（只读） |
| 换版本 / 重启服务 | **只能**用 `python switch_proxy.py`；它只停旧进程、唤醒守护进程拉新进程，不会自己起服务 |
| 改守护间隔 | 直接改 `config.json` 的 `watchdog_interval_s`，每轮重读，不用重启 |
| 改人名映射 | 直接改 `key_labels`，下一笔生效 |
| 手动补日报 | `python daily_report.py --config config.json --all` |
| 手动生成 / 刷新网页报表 | `python html_report.py --config config.json --all`（不自动跑，改了数据要重跑） |
| 改代码后验证 | `python bootstrap.py --selftest` |

守护进程每 5 秒探一次端口，掉了立刻补岗；切换工具会碰一个「立即补岗」标记，让它不用等下一轮。

**排队闸（rev10）**：`config.json` 三个参数——`max_inflight`（缺省 0＝闸关闭，行为与升级前完全一致）、`queue_beat_s`（缺省 10 秒：排队超过这个时长的流式请求先收网关心跳 `: ping`）、`gate_wait_s`（缺省 600 秒：等满照样转发，绝不拒绝）。`max_inflight > 0` 时只有对话请求（`/v1/chat/completions`、`/v1/messages`）限并发，超出的按到达顺序在网关排队；GET、`/v1/models`、stop/unload/images 等其余路径永不经闸。**改这三项保存 config 即可，无需重启，下一个对话请求即生效**（每请求重读）。等待过的请求在账本行多一个 `queue_wait_ms`；监视页排队信息在顶部模型状态卡承载（2026-11-19 人类口径改版）：排队徽标带总数数字，标签行区分「网关队列 N 个在等闸」与「引擎队列 N 个在排队」（两数据源分置：`/ext.json gate.queued` 与 `/metrics live.queued`），无排队时不显数字；独立「等待中」卡已撤销。边界见第九节第 9、10 条。

**闸卡启动配置上限（rev11a 改形）**：跟随用两个键——`gate_follow`（缺省 false＝关跟随，闸上限照旧取 `max_inflight`，行为与升级前完全一致）、`strata_config`（Strata 启动配置文件路径，支持 `@here`/相对路径）。`gate_follow: true` 时闸上限取该文件里定死的 `"parallel"` 值——**网关只卡这个上限**；引擎运行时自己往下压（显存降级、自调）属引擎内部事务，网关**不跟、不问**（人类裁定 2026-11-17 23:13：「引擎侧自己往下压和网关有什么关系？网关只负责卡住上限，引擎自己爱干什么干什么！」；rev11 的运行时轮询读法已废，见 CHANGELOG rev11a 节）。该值一次定死：网关按文件更新时间感知变更——改了启动配置的 `parallel` 保存后网关自动跟随（mtime 守卫缓存：每请求一次文件 stat，(mtime,size) 未变用缓存、零读零解析；变了才重读），无需重启网关。这里缓存的是**本地启动配置文件的新鲜度守卫**，不是引擎运行时读数——「不缓存」禁语指的是后者（不缓存引擎运行时并发读数），别混读。`strata_config` 读不到（路径空/文件缺/JSON 坏）时退回 `max_inflight` 兜底——**在岗建议：`gate_follow: true` 且 `max_inflight` 保留人类已裁并发数（现 2）当兜底**。`parallel` 字段缺席或非数值＝引擎单发语义，闸卡 1。改这些键保存即效，无需重启。跟随态的边界见第九节第 11、12、13 条。

**排队闸拦截事件独立日志（rev12）**：闸开态下，每个进闸的对话请求都在独立事件日志 `data/gate-events-YYYY-MM-DD.jsonl`（与总账 `requests-*.jsonl` 同目录、按天分文件）留下一条**决策证据**——直放＝`admitted` 一行（含网关在临界区内**核实在飞**得到的 `inflight_at_decision` 读数与当时 `limit` 快照，读数 < limit＝「核实到有空位才直放」）；被拦＝`queued` 一行（进闸瞬间，含当次在飞读数）＋`released` 一行（放行/强发时刻，含 `waited_ms` 等待毫秒、`heartbeats` 实发心跳帧数、`forced` 是否等满 `gate_wait_s` 强发）。人一眼可查「今天拦了几次、拦了谁（key/fp 与总账同口径）、等了多久、有没有等死被强发」。**决策字段与记账日志严格分离**：`event/seq/inflight_at_decision/heartbeats/forced` 只落 gate-events 文件，绝不进 `requests-*.jsonl` 键面；账本既有的 `queue_wait_ms` 保留不动，两处等待时长同一次等待的两份记录，可互证（事件日志是拦截/决策查证的权威源）。事件行字段闭集写死（三形态见 MANIFEST 2.23），**不记请求体内容**——无 messages/content/prompt 类字段，可辨识面只有 route/model/key/fp。`heartbeats`＝实发帧数口径（写失败的 ping 不算），与监视页 `beat_total`（应发计数）刻意区分，别混读。缺省零回归：闸关闭（`max_inflight=0` 且无跟随生效）时 acquire 不被调用＝零事件、零新文件、零新字节；无新增配置键。写失败口径沿总账既有纪律：单次写失败丢该行、主路径无损，`Recorder` 无 fd 坏后自愈重建（不自作主张修，要修另立票）。失败态边界见第九节第 14 条。

**看门狗划界（别混淆两套看护）**：本包看门狗 `ledger_watchdog.py` **只守护本包的记账反代**（`listen` 配置的那个端口）。Strata 官方引擎壳（`serve/server.py`）自带引擎进程看护——已对上游核对属实：官方 tag `v0.2.6` 的 pristine `serve/server.py` 里有 `restart(tries=3)`（15 秒重试间隔）与冻结引擎的 quick watchdog（`ENGINE_SILENCE_S` 缺省 300 秒，#481/#1317），配套 `serve/test_fatal_recovery.py`。这套看护与本包看门狗**无关**——本包不碰它、不依赖它，也不需要你另跑官方那套看护来保活记账反代。两套看护各管各的进程，互不重叠。

## 九、必须知道的边界（不许粉饰）

1. **反代在业务链路上**。它停了，团队就断。旧方案在旁边读日志没这个风险。守护进程和切换纪律必须一起用。
2. **本工具不改变任何使用体验——但协议本身的物理现象也不归它背**。反代对上下游都是透明中继：流式照流式（逐块转发反而更抗掐线），非流式照非流式原样返回，客户端只需要把 base_url 指过来，别的什么都不用改。「长生成期间连接上没有字节」是非流式协议的本性，**接不接本工具都一样存在**（不接时中间设备同样会读超时掐线）。长生成走非流式时，设备侧读超时建议调到 **≥600 秒**（实测见过最长 393 秒的单次生成）——这是对所有链路成立的环境建议，不是本工具的代价清单。
3. **关 key 裸连无法归人**，会记 `none`。注意畸形 `Authorization: Bearer `（有前缀无 token）是另一回事：它会记成一个陌生 8 位指纹而不是 `none`，原因见第三节第 4 个坑。
4. **切换必须等没人用**。`switch_proxy.py` 判忙的窗口是 5 分钟——因为长生成只在完成时才记账，窗口太短会把「正忙」误判成「空闲」。
5. 单个服务进程靠一个锁端口防重复（`lock_port`），重复启动会自己退出，不会两个实例抢端口。
6. 缺 `psutil` / `nvidia-smi` 只是监控降级，不影响记账。
7. **`start.sh` / `start.bat` 是前台交互式试跑**。`start.sh` 用 `exec` 把守护进程变成终端前台主进程，关掉终端、SSH 断开或会话被清理，守护进程和它拉起的服务会一起消失；`start.bat` 同理。这与 2026-11-09 17:36 那次「服务随会话消失」是同一型风险。**生产必须装 `service-examples/` 的 systemd（`Restart=always`）/ launchd（`KeepAlive`）/ 启动夹 VBS 快捷方式**（Windows 的 VBS 留在包目录、启动夹只放快捷方式，详见第二节），让守护进程脱离会话常驻；装完按第五节第 8 条自检。
8. **8 位指纹理论上可能撞码**。指纹只取 SHA-256 前 8 位十六进制（32 位空间），两把不同 key 有可能算出同一个值，人数越多概率越高。账本保留 `fp` 是为了**便于事后发现**，但代码**不做自动碰撞检测**；若团队规模大、担心撞码，可考虑把指纹加长（本次不改，加长需同时调整 `key_labels` 与历史数据口径）。
9. **排队闸的心跳承诺不可撤回（rev10）**：流式请求排队超过 `queue_beat_s` 后，网关会先替它发出响应头＋`: ping` 注释心跳帧——头一旦上线，同一连接上就再也容不下第二个 HTTP 响应（RELAY CONTRACT §4）。此后若引擎以 HTTP 错误拒绝该请求（413 超长类），错误**无法再以 HTTP 状态码出现**，只能降为流内/流断形态——账本 `error` 字段如实登记，客户端看到的是流中断，不是 4xx。不粉饰：这是排队换心跳的代价，只在「排队期间上游本身出错」这一窄窗口出现。
10. **非流式对话请求排队全程静默**（rev10）：非流式响应必须等 Content-Length 定长才能发头（协议本性，见第 2 条），所以排队中的非流式请求没有任何字节可发——客户端只会看到响应变慢；等满 `gate_wait_s` 照样放行。设备侧对非流式的读超时建议（≥600 秒）在开启闸门后同样覆盖排队时间。
11. **跟随的生效时机＝文件保存后的下一个对话请求**（rev11a）：网关按启动配置文件的更新时间感知变更（mtime 守卫：每请求一次 `os.stat`，(mtime_ns,size) 未变用缓存、零读零解析；变了才重读解析），**无轮询周期概念、无需重启网关**；且队列中等待者的 limit 是**进闸时刻的快照**（rev10 参数语义不变），新值自下一个对话请求起生效，等待中的请求不追新值。
12. **limit 下调瞬间，在飞可以超过新 limit**（rev11 沿原文）：闸绝不回收在飞请求（红线二沿 rev10）——limit 从 3 降到 1 时（含启动配置文件改小后），已在飞的 3 路照跑完，闸只是不再放新人；超额部分由引擎自身队列承接，最坏＝无闸现状。
13. **读数不可得时的回退次序**（rev11a 收缩两级）：文件读数→`max_inflight` 静态兜底→兜底 0＝闸关闭；**无「沿最后一次读得的旧值继续用」档**（rev11 的运行时读数缓存已随读源作废）。引擎运行时往下压（显存降级/自调）网关不跟——闸仍卡启动配置上限，超出引擎能力的并发由引擎自身队列承接，这是「网关只负责卡住上限」（23:13 裁定）的设计语义，非缺陷。启动配置文件中途不可读（被删/改坏 JSON）＝异常配置事故：当个请求退 `max_inflight` 兜底，下一请求文件恢复即自愈；不沿旧缓存值。
14. **事件日志写失败＝丢该行，不毁流、不进账本**（rev12）：`gate-events` 三处写点（admitted/queued/released）全部 `except Exception: pass` 吞掉——写失败不阻直放、不穿等待环、不进总账 `error` 字段；`Recorder` 与总账同款无 fd 坏后自愈重建（磁盘事故后旧 fd 不自动重开，与记账账本现纪律一致，不粉饰）。`released` 行的 `heartbeats` 只数实发成功的 ping，写失败的心跳不入该数（`beat_total` 仍按应发计数，两口径不混读）。

## 十一、真机踩坑登记（两类机型跑过之后攒下的）

以下每一条都来自实机实测，不是读代码推的。按「**症状 → 根因 → 对策**」写，方便正在排障的人直接对照。

**机型口径**：本包目前在两类机器上在岗/装配验证过——Windows 单卡终端（RTX 5090 级，Python 3.13，IPv6 接入）与 Linux 双卡工作站（RTX PRO 5000 72G + RTX 4090 24G 级，Ubuntu 系，Python 3.14）。

1. **改完 `listen` 地址族后，控制台窗口每隔几秒闪开又闪退。**
   症状：反代看起来"起不来"或端口时通时断；屏幕上启动件窗口反复弹出、秒关。
   根因：看门狗在进程内缓存旧配置的探测目标（旧脑），旧脑按旧端口每 5 秒判定"服务死了"并补拉一次，而新进程因端口/地址族对不上即起即退。
   对策：改 `listen`（尤其换地址族）后**必须重启看门狗**，让它重读新配置换脑；只重启反代进程不算。

2. **IPv6 双栈监听起步即炸，看门狗无限重拉（rev8 已修）。**
   症状：日志反复 `gaierror 11001`，服务从未监听成功。
   根因：老写法在 `server_bind()` 里才定地址族——但 socketserver 先建 socket 后调 bind，AF_INET 套接字绑 `::` 必失败。
   对策：rev8 已把地址族改为实例化前定类属性（host 含 `:` → AF_INET6，V6ONLY=0 双栈）。**升级本包即带此修；若你的机器上还跑着 002 首版，先 `git pull`。**

3. **监视页上半区（引擎读数）全灰/报错，下半区（硬件卡）正常。**
   症状：`/monitor` 打开后引擎区显示连不上或 502，看起来"监控坏了"。
   根因：引擎区数据是浏览器**直连引擎 `/metrics`**，与反代是两条独立链路。引擎刚重启、upstream 端口填错、或引擎还没起，都会只红引擎区。
   对策：先分清哪半边红——硬件卡与 `/health` 正常＝本工具无恙，去查引擎进程和 `upstream` 填值。两套数据源独立容错是设计行为，不是半页坏就整页坏。

4. **Windows 上监视器 CPU 频率常年纹丝不动（如恒 4.50 GHz），与任务管理器对不上。**
   症状：大数字百分比在涨、GHz 后缀却钉死在基准值。
   根因：注册表 `~MHz` 在 Win11 上钉死基准频率（实测常年 4500，睿频完全不进），它是废源。
   对策：rev8 起本包内置 `PdhClock`——PDH 计数器 `% Processor Performance` × `MaxClockSpeed` 基准，与任务管理器"速度"同源（实测跟随到 5.0+ GHz）。取数失败时该后缀自动省略，不谎报。**别在监视器外再拿注册表 `~MHz` 做任何容量判断。**

5. **PCIe 线路卡空闲时显示 Gen1，负载时跳 Gen5——不是读数陈旧。**
   症状：同一张卡链路代数来回跳，怀疑采样缓存过期。
   根因：NVML `pcie.link.gen/width.current` 是即时查询；空闲时 ASPM 把链路降到 Gen1 省电，搬运时升回 Gen5，属链路本态。
   对策：不用管。升降档读数经过 A/B 饱和拷贝实验验证真实（9 秒 418.8 GiB ≈ 46 GB/s，物理上只有 Gen5 量级能解释）。

6. **双卡机器想给两张卡分别配置——不需要。**
   症状：装配 Linux 双卡（异构也行，如 PRO 5000 72G + 4090 24G）时找不到显卡配置项，以为漏配了。
   根因：监控页按显卡 UUID 自动发现、逐卡绑定，配置里没有也无需有机型字段；槽位号只做展示。
   对策：什么都不用配。唯一禁忌：旧的按 nvidia-smi 槽位号分桶的注入脚本 `ext.js` 有串卡风险，已退役，**别启用**。

7. **内存/磁盘/网卡卡显示"缺 psutil"、GPU 卡显示缺 nvidia-smi。**
   症状：部分硬件卡降级，页面带降级原因。
   根因：这两项是监控增强依赖，缺失时自动降级——记账、日报、反代主链完全不受影响（两类机器都验证过）。
   对策：要补全就装进**服务实际使用的那个解释器环境**——systemd/自启件里写死哪个 python，`psutil` 就装哪个；装在别的 venv 里等于没装。

8. **计划任务/启动夹拉起时报"找不到 python"，交互终端里明明能用。**
   症状：登录自启或计划任务执行失败，日志提示解释器不存在。
   根因：登录环境没有交互 PATH（尤其便携解释器只在会话里存在）。
   对策：自启件（bat/vbs/service 文件）里解释器一律写**绝对路径**，这是 Windows 侧唯一的稳妥写法。

9. **端口口径全网要统一：门面 `8080`、引擎退环回 `8787`。**
   症状：某台机器自行改成别的口（如试跑期临时改 8090），团队接入点和文档跟着乱，切换/防火墙规则各机不一致。
   根因：门面口是全网客户端唯一入口，漂移一处就要求所有接入方记住例外。
   对策：各机只改端口**数值内**的东西（`upstream`、lock 避让值），门面缺省 `8080` 不许动；确需偏离时把它当成一次全网变更来通报，不是本机自由。

10. **改 `listen` 后"端口通但没人守"。**
    症状：防火墙放行和配置都改了，`/health` 通；但某天进程意外退出后没人拉回来。
    根因：listen、防火墙放行、看门狗重启是三件套，只做前两项就出现"通着但无守护"窗口。
    对策：三件套**同一轮**完成；改完按第五节验收清单走一遍（含第 8 条"杀掉启动会话后 `/health` 仍 200"）。
